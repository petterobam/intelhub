```

## 二、产品定位澄清

### 2.1 双层架构：「平台公共层」+「用户私有层」

这是整个产品架构的核心设计原则，必须明确：

```
┌─────────────────────────────────────────────────────────┐
│                   平台公共层（Platform Commons）          │
│                        Admin 管控                         │
├───────────────┬─────────────────┬───────────────────────┤
│  基础爬虫数据  │   政策/交易所数据  │   平台聚合知识库         │
│  (9热点平台)   │  (专业金融数据)   │   (话题/行业/图谱)       │
│  data quality ✅│  data quality ✅ │   data quality ✅       │
└───────────────┴─────────────────┴───────────────────────┘
                         ↓ 只读访问
┌─────────────────────────────────────────────────────────┐
│                   用户私有层（User Space）                │
│                  每个用户独立命名空间                      │
├───────────────┬─────────────────┬───────────────────────┤
│  用户兴趣配置  │   用户订阅源      │   用户私有知识库         │
│  (tags/话题)  │  (公众号/YT/B站) │   (个人日报归档/上传)     │
│  user-owned   │  user-owned      │   user-owned           │
└───────────────┴─────────────────┴───────────────────────┘
                         ↓ AI 读取两层
                  个性化报告 / 个性化AI对话
```

**关键原则**：
- 用户**可以**过滤、定制、扩展，但**不能**修改或干扰平台公共层数据
- AI 分析时同时读取「平台数据（按用户兴趣过滤）」+「用户私有数据」
- 每个用户的数据存放在 `data/users/{user_id}/` 下，物理隔离

### 2.2 五个版本重新解析

原始规划的5个版本，用架构语言重新表述：

| 版本 | 产品名 | 用户控制维度 | 数据来源 | 交付方式 | 定价参考 |
|------|--------|------------|---------|---------|---------|
| **V1 纯推送版** | 智能日报 | 无（平台固定内容） | 平台数据 | 邮件 + H5链接 | 9.9-19.9/月 |
| **V2 可定制版** | 个人智报 | 兴趣标签 + 平台偏好 | 平台数据（按标签过滤）| 邮件 + 专属H5 | 29.9/月 |
| **V3 订阅源版** | 全源追踪 | 自维护内容源列表 | 平台数据 + 用户源 | 邮件 + 专属H5 | 待定 |
| **V4 知识库版** | 智识归档 | 个人知识库管理 | 平台+用户源+历史报告 | 邮件+H5+查询接口 | 待定 |
| **V5 上传版** | 研究助手 | 上传私有数据源 | 全部 + 用户上传 | 邮件+H5+对话 | 待定 |

> **注意**：五个版本是**叠加关系**，不是并列关系。V5 的用户拥有 V1-V4 的全部能力。

## 三、需求详细拆解

### REQ-01：用户分层体系（User Tier System）

**问题**：当前 User 表只有 `role: admin/user`，没有付费等级，无法按版本控制功能权限。

**需求**：
- 在 User 表增加 `tier` 字段：`free | v1 | v2 | v3 | v4 | v5`（或用数字 0-5）
- 各 tier 对应功能访问权限矩阵

**功能权限矩阵**：

| 功能 | free | v1 | v2 | v3 | v4 | v5 |
|------|------|----|----|----|----|-----|
| 查看平台报告 | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| 邮件推送（固定内容）| ❌ | ✅ | ✅ | ✅ | ✅ | ✅ |
| H5日报链接 | ❌ | ✅ | ✅ | ✅ | ✅ | ✅ |
| 设置兴趣标签 | ❌ | ❌ | ✅ | ✅ | ✅ | ✅ |
| 个性化报告生成 | ❌ | ❌ | ✅ | ✅ | ✅ | ✅ |
| 添加内容订阅源 | ❌ | ❌ | ❌ | ✅ | ✅ | ✅ |
| 个人知识库 | ❌ | ❌ | ❌ | ❌ | ✅ | ✅ |
| 文件上传 | ❌ | ❌ | ❌ | ❌ | ❌ | ✅ |
| AI对话（平台数据）| ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| AI对话（个人KB）| ❌ | ❌ | ❌ | ❌ | ✅ | ✅ |

**技术任务**：
- [ ] User 模型增加 `tier` 字段（String，默认 `free`）

### REQ-02：用户兴趣配置（User Profile & Tags）

**问题**：当前用户没有任何兴趣偏好配置，所有人收到同一份报告。

**需求**：
- 用户可以配置「关注实体」：公司（华为、特斯拉）、人物（马斯克）、话题（新能源、AI）
- 用户可以配置「关注平台」：从平台支持的9个热点源中勾选
- 配置以 JSON 形式存在数据库，低频变更

**数据模型**：新建 `UserProfile` 表（或扩展 User 表）：
```
UserProfile:
  user_id       → FK → User.id
  interest_tags → JSON  # [{type: "company", value: "华为"}, ...]
  platforms     → JSON  # ["weibo", "zhihu", "36kr"]
  report_time   → String  # "08:00" 每日报告时间
  timezone      → String  # "Asia/Shanghai"
  updated_at    → DateTime
```

**标签分类**（平台预设类型，用户只选值不定义类型）：
- `company`：公司/品牌（华为、苹果、比亚迪、OpenAI...）
- `person`：人物（马斯克、黄仁勋、任正非...）
- `topic`：话题/赛道（新能源、AI大模型、半导体、地产...）
- `sector`：行业（科技、金融、医疗、消费...）

**技术任务**：
- [ ] 新建 `UserProfile` 模型
- [ ] `/api/v1/profile/interests` CRUD API
- [ ] 前端「我的偏好」页面：多选标签界面
- [ ] 平台维护一份「可选标签词库」（JSON文件或数据表）供用户选择
- [ ] 标签词库管理 Admin 界面（增删改标签）

### REQ-03：个性化报告生成（Personalized Report Engine）

**问题**：报告生成完全基于全量平台数据，无法针对个人兴趣过滤。

**需求**：
- 系统每天为每个 V2+ 用户生成一份「个人专属日报」
- AI 读取平台数据时，按用户的 `interest_tags` 过滤相关条目
- 每个用户的报告存放在 `data/users/{user_id}/reports/daily/`

**报告生成流程**：

```
1. 调度触发（每天 N 点，按用户 report_time 配置）
2. 加载用户 interest_tags + platforms
3. 从平台聚合数据中筛选相关条目（关键词匹配 + 平台过滤）
4. 构建个人上下文 prompt（包含用户兴趣作为筛选指令）
5. AI 分析引擎生成个人日报
6. 保存到用户目录 + 生成 H5 静态页
7. 发送邮件（链接指向 H5 页面）
```

**关键设计决策**：AI 生成个人报告时，Prompt 中应携带用户兴趣：

```
系统Prompt追加：
"本次报告的目标用户关注：[华为, 新能源, AI大模型]
请优先提炼与这些关键词相关的内容，忽略无关条目。"
```

**技术任务**：
- [ ] 新建 `PersonalizedReportTask` 调度器（扫描所有V2+用户，逐个生成）
- [ ] `analysis/personalized/` 新模块，封装个人报告生成逻辑
- [ ] 报告输出路径规范：`reports/users/{user_id}/daily/{date}.md`
- [ ] 同步生成 H5 静态页：`static/reports/{user_id}/{date}.html`
- [ ] 报告关联 User，存入 `report` 表（增加 `user_id` 字段）
- [ ] 前端「我的报告」页面（用户只看自己的）

### REQ-04：静态 H5 日报页（Static H5 Report Pages）

**问题**：当前没有面向普通用户的静态展示页，邮件只能推送文字，无法推送精美页面链接。

**需求**：
- 每份报告（平台报告 + 个人报告）都生成一个静态 H5 页面
- 页面 URL 格式：`/reports/{report_id}` 或 `/r/{short_id}`
- 支持两种访问控制：
  - 平台公共报告：公开访问（方便传播引流）
  - 个人专属报告：需要登录/Token验证
- 页面设计：纯静态，移动端友好，加载快

**页面内容结构**：
```
- 报告标题 + 日期
- 核心摘要（3-5条 highlights，带平台来源图标）
- 各话题展开（可折叠）
- 原文链接列表
- IntelHub 品牌 footer（引流入口）
```

**技术任务**：
- [ ] 报告生成时同步生成 HTML 文件（Jinja2模板渲染）
- [ ] Flask 路由 `/r/<report_id>` 服务静态报告页
- [ ] 设计移动端优先的 HTML 模板（inline CSS，无外部依赖）
- [ ] 个人报告页增加 Token 访问控制（URL 中携带 access_token）
- [ ] 邮件模板中嵌入 H5 链接 + highlight 预览

### REQ-05：用户内容订阅源（Content Source Subscriptions）

> ⚠️ **命名冲突澄清**：当前代码中的 `Subscription` 是「邮件推送订阅」，而这里的需求是「内容源订阅」（关注的平台/账号）。两者是不同概念，需要用不同的表名区分。

**需求**：V3+ 用户可以维护自己关注的内容源列表，系统会定期抓取这些源的内容，纳入用户的个性化报告。

**支持的内容源类型**（按优先级排序）：
1. **RSS Feed**（最易实现，覆盖广）
2. **微信公众号**（需特殊处理）
3. **Bilibili UP主**（有开放API）
4. **YouTube 频道**（有开放API）
5. **X/Twitter 账号**（API限制多）
6. **Facebook**（较难）

**数据模型**：新建 `UserSource` 表：
```
UserSource:
  id          → String PK
  user_id     → FK → User.id
  type        → String  # rss | bilibili | youtube | wechat | ...
  source_id   → String  # 频道ID/账号ID/RSS URL
  display_name→ String  # 用户自定义别名
  enabled     → Boolean
  last_fetched→ DateTime
  item_count  → Integer
  status      → String  # active | error | rate_limited
  created_at  → DateTime
```

**采集机制设计**：
```
用户源采集 ≠ 平台采集
  - 独立的任务队列（不占用平台采集资源）
  - 每个用户源独立调度（频率受限，如每6小时一次）
  - 数据存放在 data/users/{user_id}/sources/{source_id}/
  - 采集失败不影响平台主流程
```

**平台管控边界**：
- 用户只能添加「支持类型」内的源（不能任意爬取）
- 每个用户源数量上限（如 V3: 10个，V4: 30个，V5: 100个）
- 对需要登录才能访问的源，由用户自行提供 Cookie/Token（平台不存储账号密码）

**技术任务**：
- [ ] 新建 `UserSource` 模型（区别于现有 `Subscription`）
- [ ] `/api/v1/user-sources` CRUD API（限本人操作）
- [ ] 各类型爬虫适配器：`crawlers/user_sources/rss.py`, `bilibili.py`, `youtube.py`
- [ ] 用户源调度器（独立线程/队列）
- [ ] 前端「我的数据源」管理页面
- [ ] 源数量限额检查（按 tier）
- [ ] Admin 可查看所有用户源状态

### REQ-06：爬虫脚本扩展（Crawler Script Expansion）

**问题**：当前平台只有9个热点平台 + 4类专业数据，对于个性化内容场景远远不够。

**需求分两类**：

#### A. 平台级扩展（Admin管控，提升公共数据质量）

优先级高的新增来源：

| 类别 | 目标数据源 | 价值 |
|------|-----------|------|
| **科技科创** | 少数派、IT之家、CSDN热榜、GitHub Trending | 科技用户覆盖 |
| **财经深度** | 华尔街见闻、第一财经、Wind资讯 | 投资分析质量 |
| **国际视野** | Reuters、Bloomberg Headlines、FT中文 | 全球视野 |
| **产业数据** | 招商证券研报标题、同花顺热门 | 研报追踪 |
| **政策扩展** | 地方发改委（北上广深）、各省政府 | 区域政策 |

每个新爬虫需要：
- `crawlers/scripts/{platform}/` 目录下的 Node.js 或 Python 脚本
- 标准化输出格式（`{title, url, source, timestamp, category}`）
- 在 `PLATFORMS` 配置中注册
- 配套的降级 fallback

#### B. 用户源适配器（支撑 REQ-05）

| 类型 | 实现方案 | 优先级 |
|------|---------|------|
| **RSS/Atom** | `feedparser` 库，通用 | P0 |
| **Bilibili UP主** | 调用 B 站公开 API | P1 |
| **YouTube 频道** | YouTube Data API v3 | P1 |
| **微信公众号** | 通过RSS代理（如 WeRSS/RSSHub）| P2 |
| **X/Twitter** | Twitter API v2（付费限制）| P3 |

**技术任务（平台级）**：
- [ ] `crawlers/scripts/tech/` 目录：少数派、IT之家、GitHub Trending
- [ ] `crawlers/scripts/finance/` 目录：华尔街见闻、第一财经
- [ ] `crawlers/scripts/international/` 目录：Reuters、FT中文
- [ ] 更新 `HotTopicsRunner.PLATFORMS` 字典
- [ ] 更新 `KnowledgeBaseManager` 行业分类以覆盖新领域

**技术任务（用户源适配器）**：
- [ ] `crawlers/user_sources/base.py`：基类，定义 `fetch() -> List[Item]` 接口
- [ ] `crawlers/user_sources/rss.py`：RSS/Atom 通用适配器
- [ ] `crawlers/user_sources/bilibili.py`：B站 UP主动态
- [ ] `crawlers/user_sources/youtube.py`：YouTube 频道最新视频
- [ ] 标准 Item Schema 定义（与平台数据格式兼容）

### REQ-07：用户私有知识库（User Knowledge Base）

**问题**：当前知识库是全局共享的，没有用户隔离，也没有「个人历史报告归档转知识库」的能力。

**需求**：
- 每个 V4+ 用户有独立的知识库命名空间
- 用户的历史日报自动归档进个人知识库
- 用户的 KB 可以被 AI 对话检索（仅本人可见）
- 支持导出为 Markdown（Obsidian兼容）

**目录结构设计**：
```
data/users/{user_id}/
├── sources/              # 用户源采集的原始数据
│   ├── {source_id}/
├── reports/              # 用户个性化报告
│   └── daily/
│       ├── 2026-05-07.md
│       └── 2026-05-08.md
├── uploads/              # 用户上传文件（REQ-08）
│   └── docs/
└── kb/                   # 用户知识库（从reports + uploads构建）
    ├── topics/           # 个人话题索引
    ├── timeline/         # 时间线视图
    ├── entities/         # 实体追踪（关注公司/人物的历史动态）
    └── index.json        # KB 元数据
```

**知识库构建逻辑**：
```
输入：用户历史日报 + 用户上传文件
↓
实体提取（公司、人物、话题 - 基于用户 interest_tags）
↓
时间线构建（同一实体跨日期的动态追踪）
↓
话题聚类（相似内容归组）
↓
输出：
  - 实体追踪文件（如 "华为-timeline.md"）
  - 话题摘要文件
  - 全文搜索索引
```

**AI 对话工具扩展**：
- 当前 AI 对话只能读取平台数据
- V4+ 用户对话时，额外注入用户 KB 工具
- `chat_search_user_kb(user_id, query)` — 搜索个人KB
- `chat_read_user_timeline(user_id, entity)` — 查某实体历史

**技术任务**：
- [ ] `KnowledgeBaseManager` 支持 `user_id` 参数（实例化时指定用户目录）
- [ ] 个人KB构建任务（在生成日报后自动触发）
- [ ] `/api/v1/user-kb` API（stats, search, graph, topics）
- [ ] Chat API 中，V4+ 用户注入个人KB工具

### REQ-08：用户文件上传（File Upload & Ingestion）

**问题**：当前没有文件上传能力，用户无法将自己的研究材料纳入分析。

**需求**：V5+ 用户可以上传文件，系统解析后纳入个人知识库。

**支持的文件类型**：
| 类型 | 解析方案 | 优先级 |
|------|---------|------|
| PDF | `pypdf2` / `pdfminer` | P0 |
| TXT / Markdown | 直接读取 | P0 |
| Word (.docx) | `python-docx` | P1 |
| 网页 URL | `requests` + `BeautifulSoup` | P1 |
| 图片（含文字）| OCR（可选，后期） | P3 |

**上传限制**（按 tier）：

**处理流程**：

上传 → 格式检测 → 内容提取 → 分块存储 →
纳入用户KB → 触发KB重建 → AI可读取
```

### REQ-09：数据质量与平台边界保护

**问题**：在开放用户定制的同时，必须保证平台数据质量不被干扰。

**需要建立的边界规则**：

#### 原则一：平台层只读
- 用户永远不能修改/删除 `data/raw/`、`data/processed/`、全局 `knowledge_base/`
- API 层严格检查：所有写操作只能写到 `data/users/{user_id}/`

#### 原则二：用户层完全隔离
- 用户 A 的数据对用户 B 不可见（API 和文件系统都要检查）
- 知识库实例化时必须传入 `user_id`，不能默认读全局

#### 原则三：用户源不影响平台调度
- 用户源采集任务在独立线程池运行（不占用 APScheduler 主队列）
- 用户源失败不触发告警（不影响系统健康分）
- 用户源采集频率上限：每6小时/源（防止滥用）

#### 原则四：内容质量最低标准
- 用户上传文件需要通过基本格式校验
- 用户源内容纳入个人KB前进行基础过滤（去重、过短内容过滤）
- 个人报告中明确标注「平台数据」vs「个人来源」（来源透明度）

**技术任务**：
- [ ] 文件路径检查中间件（所有写 API 验证路径在用户命名空间内）
- [ ] 用户源任务使用独立线程池（与 APScheduler 隔离）
- [ ] 用户源采集频率限制器
- [ ] 报告中标注数据来源（系统数据 / 个人订阅 / 用户上传）

### 5.2 数据库模型变更汇总

### 5.3 新增 API 路由规划

  POST /                      # 上传

### 5.4 关键约束与风险提示

| 风险 | 说明 | 应对 |
|------|------|------|
| **性能**：用户量增加后个性化报告生成耗时 | 每个用户串行调用 AI 分析 | 使用异步任务队列，分批生成；结果缓存 |
| **成本**：每个用户每天调用一次 LLM | Token 消耗线性增长 | 兴趣匹配过滤后缩减上下文长度；考虑摘要缓存 |
| **隔离**：文件路径遍历攻击 | 用户构造 `../` 路径 | 所有文件操作用 `os.path.abspath` 验证前缀 |
| **爬虫合规**：用户源扩展可能触碰法律边界 | 微信公众号/YouTube有版权/服务条款 | 初期只支持 RSS（用户主动授权的源）；明确 ToS |
| **存储增长**：用户上传 + KB 积累 | 500MB * 用户数 | 早期手动管理；后期引入 S3/OSS |
